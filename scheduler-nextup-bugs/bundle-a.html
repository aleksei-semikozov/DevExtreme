[Won't Fix] #738 — Scheduler — Recurrence icon overlaps the truncated title in narrow all-day cells

Designers · PMs · Support · Developers

What's the issue?

In the week / work-week / day views, when an all-day appointment is too narrow to show its full text, the title is truncated with an ellipsis. If that appointment also carries a recurrence rule, its recurrence icon is drawn on top of the ellipsis instead of beside it. For the head/tail segments of a multi-day appointment the "continues" arrow can collide with the recurrence icon in the same corner.

Root cause: in the base theme the all-day block reserves right-padding ($scheduler-appointment-reduced-content-padding: 40px) only for .dx-scheduler-appointment-reduced (the continuation/"reduced" icon), not for .dx-scheduler-appointment-recurrence-icon — see devextreme-scss/.../scheduler/_index.scss:208-216. The month view already reserves this space (_index.scss:666-672), which is why month renders correctly.

Why don't we want to fix it?

  • Pure cosmetic. The appointment stays fully interactive — click, tooltip and editing all work; only two glyphs overlap visually.
  • Narrow edge only. It appears only when the column is too narrow to show the text and the appointment is recurring; widening columns or reducing grouping removes it.
  • Month view is already correct, so this is not a systemic layout problem.
  • High cost, low value. A real fix means reserving padding and repositioning every icon combination (reduced + recurrence + "continues" arrow), touching markup/a11y, and re-baselining scheduler screenshots across all themes — disproportionate to a minor overlap in a rare configuration.

Workarounds

  • Give all-day cells more width (fewer horizontal groups / wider container) so the title doesn't truncate.
  • Use an appointmentTemplate / appointmentTooltipTemplate to control icon placement or surface the recurrence state your own way.

[Won't Fix] #1699 — Scheduler — Appointment can be resized one cell past its resource group (horizontal grouping)

Designers · PMs · Support · Developers

What's the issue?

With horizontal resource grouping, resizing an appointment lets its drag preview extend exactly one cell into the neighbouring resource group before snapping back. The persisted appointment is not corrupted — it stays within its own group; only the resize preview overshoots by a single cell.

Resize bounds come from getResizableAppointmentArea / getGroupBounds in m_subscribes.ts:150-177. The horizontal/month branch returns group bounds that are one cell wider than the group; the vertical branch returns tight bounds.

Why don't we want to fix it? (pending your ruling)

  • Maximum overshoot is one cell, and it is preview-only. The committed result is always correct — an appointment cannot actually be dropped into the wrong group, so there is no data-integrity impact.
  • But there is a genuine H/V inconsistency worth a decision: horizontal grouping permits the 1-cell overshoot while vertical grouping does not. The core question is which behaviour is canonical — do we tighten horizontal to match vertical, or accept the 1-cell slop?
  • If we align them, the fix is modest (correct the horizontal group bounds in m_subscribes.ts and re-baseline the resize e2e), but it is code + tests we'd only spend for a visual nicety.

Recommendation: Won't Fix — unless you consider the horizontal-vs-vertical inconsistency worth aligning, in which case reclassify as a small fix.

Workarounds

  • None required for correctness — the appointment cannot be committed outside its group.

#1834 — Scheduler — Wrong day name in timeline views on DST spring-forward

Designers · PMs · Support · Developers

What's the issue?

In the timeline views (timelineMonth / timelineDay), under a timezone that observes DST, the day headers around the spring-forward boundary show the wrong weekday. Confirmed with Playwright (timezoneId: 'Europe/Belgrade', currentDate: '2024-03-31', offset: 120): 31 March is labelled 'Sat' instead of 'Sun', and 'Sat' appears twice in the header row.

Note: the fact that there is no 2:00 AM slot that day is correct — the clocks jump 02:00 → 03:00. Only the day name is defective.

Root cause: getDateByCellIndices (view_data_generator.ts:605+) builds each cell's date by adding a fixed 24-hour stride to startViewDate (getMillisecondsOffset → interval * cellIndex, where interval = toMs('day') for timeline month). The spring-forward civil day is only 23 hours, so the accumulated milliseconds drift by one hour and a cell lands in the previous civil day — producing the duplicated 'Sat'. The existing DST-correction branch (isStartViewDateDuringDST / getTimezonesDifference) doesn't cover this timeline path.

Why fix it (rather than Won't Fix)?

  • It's a correctness defect. A wrong weekday label reads as a plain bug to any user, no matter how narrow the trigger — "Won't Fix" is a weak stance for an incorrect date.
  • Contained blast radius and cheap to lock down. The fix is local to the timeline date generation, and the issue's own TODO already calls for a Jest snapshot of all visible dates — exactly the guard we'd add.

Recommended fix

  • In getDateByCellIndices, step the per-cell date in calendar-day units (or apply the timezone-difference correction) for the timeline path, instead of a fixed millisecond stride, so the day boundary is honoured across the DST change.
  • Add a Jest snapshot of the visible day names for tz = Europe/Belgrade around 2024-03-31 (and an autumn fall-back case) to prevent regressions.

Card estimate: 5.
