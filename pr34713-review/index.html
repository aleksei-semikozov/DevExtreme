Ревью PR 34713 — что задевает правка за пределами сгруппированного ресурса

Две колонки — две разные сборки одного и того же кода: слева merge-base 74a1770 (до правки), справа head PR 34713 2cdc4e2. Обе собраны из ветки feature/scheduler-multilevel-grouping.

Основной сценарий фикса — ресурс, перечисленный в groups — работает верно и здесь не оспаривается. Ниже два сценария, которые правка задевает непреднамеренно: условие в getResourceEditorDataSource смотрит только на hasHierarchy и ничего не знает ни про groups, ни про опции исходного dataSource.

Сценарий 1. Иерархический ресурс, которого нет в groups

groups: ['ownerId']; ресурс roomId с parentIdExpr в группировке не участвует. Встреча «Совещание в Board rooms» назначена на родительский узел roomId: 'board'.

  1. Обратите внимание: встреча отрисована в обеих колонках — значение рабочее, потому что по листьям фильтруются только ресурсы из groups (is_appointment_matched_resources.ts:19 получает лишь groupResources()).
  2. Откройте «Совещание в Board rooms» двойным щелчком и посмотрите на поле Room и на строку состояния над расписанием.

Ожидается: поле Room показывает «🏢 Board rooms», родителя видно и можно выбрать.
Фактически справа: поле Room пустое, «Board rooms» в списке нет — при том что расписание это значение отображает.

Чем хуже: у встречи, которая нормально живёт в расписании, форма показывает пустое поле ресурса — пользователь видит «комната не назначена» и не может вернуть прежнее значение.

Сценарий 2. Ленивый ресурс: теряются filter и sort

Тот же ресурс вне groups, его dataSource задан объектом опций: { store: rooms, filter: ['active', '=', true], sort: 'text' }. Ни одна встреча на roomId не ссылается, поэтому к моменту открытия формы ресурс не загружен: Scheduler предзагружает только ресурсы из groups (scheduler.ts:484), а loadAppointmentsResources — только те, на которые ссылаются встречи. Форма идёт по ленивой ветке и пересобирает DataSource из одного лишь store().

  1. Откройте «Встреча без комнаты» двойным щелчком.
  2. Разверните список Room и сравните состав и порядок с левой колонкой.

Ожидается: только активные комнаты, отсортированные по названию.
Фактически справа: в списке есть «Room 12 (архивная)», которую отсекал filter, а порядок — как в сторе, без sort.

Чем хуже: пользователь может выбрать ресурс, который разработчик намеренно скрыл через filter; такое же расхождение получают sort, select, map и postProcess. Причём тот же ресурс после загрузки (ветка leafData) отдаёт уже отфильтрованный список — состав списка зависит от тайминга.
